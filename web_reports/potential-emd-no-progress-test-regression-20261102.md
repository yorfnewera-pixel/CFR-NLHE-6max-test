Дата: 2026-11-02. Результат: test-only диагностика и согласованный минимальный production-патч пройдены. Генератор не запускался.

## Область проверки

В `native/hu20-buckets/src/lib.rs` добавлена отдельная fixture из сохранённого
`emd-failure-flop-clustering.txt`:

- стадия: `flop-clustering`;
- `point_index=1`;
- `centroid_index=9`;
- размерность: `10`;
- исходная ошибка: `EmdError::NoProgress`.

Старая fixture `ranks=5` сохранена без изменения. На этапе диагностики добавленные
трассы находились внутри `#[cfg(test)]`; последующий production-патч `try_emd`
описан ниже. CLI не менялся.

## Установленная причина

Прямой characterization-тест до production-патча подтвердил: `try_emd` на fixture
возвращает именно `EmdError::NoProgress`.

Test-only трасса записывает для каждой augmentation `amount`, `delivered` до и
после, а также факт изменения forward и reverse residual capacities. Она
подтвердила гипотезу округления: есть шаг с `amount > 0`, неизменившимся
`delivered` и изменившимся residual-графом. Поэтому критерий прогресса по одному
лишь `delivered` некорректен для этой fixture.

Test-only вариант, сохраняющий ограничение `required_mass - delivered`, нужен
только для воспроизведения трассы. Отдельный вариант без этого ограничения
вычисляет bottleneck только по capacities пути, завершает полный транспорт и
совпадает с независимым оракулом. Это подтверждает обоснованность предлагаемого
исключения данного ограничения из production-патча.

Test-only кандидат считает транспорт завершённым только при одновременном
исчерпании residual supply и residual demand. Прогресс augmentation определяется
фактическим изменением хотя бы одной residual capacity — forward или reverse;
изменение каждого ребра пути не требуется.

## Предложение минимального production-патча

Production-изменение было отдельно согласовано и выполнено после этой диагностики.

1. В `try_emd` определять успех по residual supply и residual demand, а не только
   по накопленному `delivered`.
2. Определять bottleneck augmentation минимумом residual capacities построенного
   пути; не ограничивать его выражением `transport_mass - delivered`, поскольку
   трасса подтверждает возможное округление суммы delivered.
3. Возвращать `NoProgress` лишь когда положительная augmentation не изменила ни
   одну forward/reverse residual capacity.
4. Сохранить отдельные ошибки для неполного транспорта и исчерпания бюджета;
   частичную стоимость не считать успешным результатом.

Не предлагались и не применялись: увеличение epsilon, возврат частичной
стоимости как успеха, изменение метрики или кластеризации.

## Итог production-патча

В `try_emd` bottleneck теперь ограничивается только residual capacities найденного
пути. Прогресс требует изменения хотя бы одной forward/reverse residual capacity;
неизменившийся `delivered` сам по себе больше не является ошибкой. Завершение
проверяет оба residual supply/demand с прежним допуском; после последней
разрешённой augmentation эта проверка выполняется повторно до возврата
`IterationLimit`.

Новая fixture переведена в production-регрессию успешного полного транспорта с
oracle-cost. Production-регрессии ranks=5 и малого независимого reference также
пройдены. Бюджет итераций, типизированные ошибки и проверки конечности стоимости
сохранены.
